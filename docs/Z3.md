## Base patch (done)

`tools/z3/build_z3_ips.sh` extracts z3randomizer at the pin, copies the JP 1.0 ROM (`rom/alttp_jp_v1.sfc`, MD5
`03a63945398191337e896e5771f77173`) and runs `asar --fix-checksum=off LTTP_RND_GeneralBugfixes.asm`, exactly what
`UpdateBuildRecord` does. asar grows the ROM to 2 MB.

- Built ROM MD5: `edc01f3db798ae4dfe21101311598d44`, which equals `Rom::HASH`.
- `patches/z3_base.ips` (186891 bytes, MD5 `21c1f78916d2ee4a81b6d34f511b3f83`): written by `tools/z3/make_ips.py`
  against the JP ROM zero-padded to 2 MB, then replayed and compared with the built ROM. A reader must grow the ROM to
  2 MB (zero-filled) before applying it, as `Rom::resize()` does.
- `tools/z3/gen_z3_ips_c.py` embeds it as `Z3_BASE_IPS` / `Z3_BASE_IPS_LEN` (`build/z3gen/z3_ips_data.c`, like
  `gen_sm_ips_c.py`). No host Makefile references it yet.

## PHP oracle

`tools/z3/oracle/Dockerfile`: `php:8.1.29-cli-bookworm` (alttpr's `platform-overrides` is PHP 8.1), composer 2.7.7,
alttpr fetched at the pinned commit, `composer install --no-dev --no-scripts` from its `composer.lock` (which pins
z3/randomizer at `dcb0a2b4`). Image `smz3u-z3oracle:219fcafd`; build or run with `tools/z3/oracle/oracle.sh`.

Seeding: alttpr's only randomness is `get_random_int()` (`app/Helpers/number.php`, `random_int`). The Dockerfile
rewrites its body to `empty($GLOBALS["Z3_ORACLE_SEEDED"]) ? random_int($min, $max) : mt_rand($min, $max)`;
`oracle_seed(n)` in `z3oracle.php` calls `mt_srand(n, MT_RAND_MT19937)` and sets the flag. Only the container's copy
is patched; without a seed the generator is upstream's. The Enemizer's own seed is a `random_int` too: the oracle takes
it from the case (`enemizer_seed`).

`tools/z3/oracle/z3oracle.php` verbs (all print names, not numbers):

| Verb | Mirrors | Prints |
|---|---|---|
| `schema <out.json>` | `gen-cli schema` | build, hash, the option lists of `config('alttp.randomizer.item')`, item names |
| `vectors <n> <seed> <out>` | `gen-cli vectors` | ItemCollection helpers (`canLiftRocks` ... `hasHealth/12`) and every `Boss::canBeat` for random settings and inventories |
| `worldvectors <n> <seed> <out>` | `gen-cli worldvectors` | random settings, prizes, medallions, a few placed keys, inventory; `canEnter`/`canComplete` per region and `canAccess` per location |
| `placementbatch <cases.jsonl> <out>` | `gen-cli placementbatch` | full `Randomizer` run per seeded case: placement, pre-collected items, bosses, `isWinnable` |
| `checkplacement <cases.jsonl> <out>` | (new) | a placement made by the C filler read back through PHP: `isWinnable` and unreached locations |
| `placementrom <base.sfc> <case.json> <out.sfc>` | `prepSeed` | a seeded run of the whole generator (crystals, `randomize()` with texts, credits and hints, `writeToRom`, `isWinnable`, the Enemizer when bosses are shuffled, tournament, Rom.php's cosmetic setters), seed string `str_pad("VT <seed>", 21)`, hash icons from the case; with a `placement` in the case, the Customizer path instead |
| `rombatch <base.sfc> <cases.jsonl> <outdir>` | (new) | `placementrom` per line, `<outdir>/<n>.sfc` |
| `textdata <out.json>` | (new) | the data `tools/z3/gen_z3_text.py` turns into `z3_text_gen.c`, plus encoder samples |

Paths are relative to the caller's directory (the script `chdir`s to Laravel's root, so it resolves them first).
The Enemizer run (`enemize()`) is prepSeed's: `writeToRom($rom, true)` has written the seed string and hash by then
(the Enemizer refuses a ROM without "VT" at 0x7FC0), so the oracle writes both first; the Enemizer's input is `--rom`
plus `--base` plus the write log, so `--rom` is the patched base ROM and `--base` an empty `storage/patches/<hash>.json`.
The image adds `libunwind8` and sets `System.Globalization.Invariant` in `EnemizerCLI.Core.runtimeconfig.json`: the
.NET Core 2.0 build finds no ICU it knows on bookworm and reads no environment switch for it.
Every case resets `World::$max_world` to 1: alttpr builds one world per request, and the id shows up in names.
Crystal counts are kept as the request's strings unless drawn, as `prepSeed` does (`crystals.tower === 0` in
`writeToRom` only pre-opens the tower for a random 0). Fixed on the first run: items printed by `getRawName()` (with
`getName()` the `:1` world suffix made every name unknown), and `checkplacement` reads reachability from a fresh
`collectItems()` and `canAccess` (`getCollectableLocations()` is cached on first use and listed every location).

## Logic transpiler (every world state and logic: parses completely)

`tools/z3/port_world_php.py` reads `World/Standard.php`, `World/Open.php` and `World/Inverted.php` (26 region keys
each; Retro is Open's), the region classes they use, `Boss.php`, `Item.php` and `config/logic.php`, and writes
`core/z3gen/z3_world_gen.{h,c}`. It parses the PHP into an expression tree (closures, `if`/`return`,
ternaries, `in_array`, `is_a`, `instanceof`, `itemInLocations`, local closures such as Turtle Rock's `$upper`, the
region's own methods such as Inverted Turtle Rock's `enterTop`), so nothing is hand-patched: the run ends with no TODO.

Output: 179 items (176 + the aliases UncleSword, ShopKey, ShopArrow) with class and byte, 12 bosses, 26 regions,
241 locations (kind, region, first ROM address), 41 shops, 48 config keys (`Z3Cfg`, enums for the string ones), and
`z3_region_enter`, `z3_region_complete`, `z3_loc_req`, `z3_loc_fill`, `z3_loc_always`, `z3_shop_req`,
`z3_boss_beat`, `z3_region_item`, `z3_loc_exists`, `z3_shop_exists`, `z3_loc_named`, `z3_world_defaults`,
`z3_cfg_defaults`, `z3_cfg_logic`. Where the world states use different classes the dispatch picks by
`cfg.mode_state` (Retro takes Open's). The glitch switches in the closures (`canOWYBA`, `canBootsClip`, ...) are
config flags filled from `config/logic.php`; with No Logic every dispatch returns its default, as `World::__construct`
then never calls `initalize()`.

Inverted, as the PHP has it:
- Every Inverted dungeon class extends Standard's and starts with `parent::initalize()`: the walk runs the parent's
  body, then the child's, and keeps each closure with the class that wrote it (its locals are that class's). A
  `setRequirements($this->can_complete)` takes the closure set at that moment, not a later override.
- Its constructors move four locations to another region (Ganon to North East Light World, Link's House to South
  Dark World, Ether Tablet and Spectacle Rock to East Death Mountain), add Bomb Merchant, take out the Dark Death
  Mountain Fairy shop and restock the Dark World Lake Hylia Shop. The location list is the union, region by region
  (each world's own list is a subsequence of it, which the script asserts, so walking it and skipping what
  `z3_loc_exists` rules out gives PHP's `getLocations()` order). A moved location has an id per region
  (`Z3_LOC_Ganon_Inverted` ...); `z3_loc_named` is `World::getLocation(name)`.
- Three slips in alttpr's Inverted classes run as PHP runs them: `has('PegasusBoot')` (Escape) finds no such item,
  a bare `getRegion('West Death Mountain')` (Palace of Darkness) is a truthy object, and `hasABottle(2)` (Light World)
  drops its argument.

Hand-written in `core/z3gen/z3_world.{h,c}`: `Z3Items`, `Z3World`, `ItemCollection::has` and its helpers,
`World::__construct`'s config switches (`z3_cfg_derive`), `Location::canAccess`/`canFill`, `Region::canFill`,
`World::collectItems`.

## Seeded PRNG (done)

`core/z3gen/z3_rng.{h,c}`: PCG32 (XSH RR), seeded through splitmix64. Integer-only, 16 bytes of state, cheap on the
3DS's ARM11, and with published reference outputs (`z3_rng_init_pcg` is `pcg32_srandom_r`). `z3_rng_int(min, max)`
is `get_random_int` (inclusive, unbiased by rejection), `z3_rng_shuffle` draws in `fy_shuffle`'s order.

`z3_generate(s, jp_rom, jp_len, out_rom, out_cap, seed, hash_out, icons_out)`: JP ROM grown to 2 MB with zeros, base

**Draw order.** Every `get_random_int`, `fy_shuffle`, `Collection::random` and `randomCollection` is a `z3_rng_int`
in the PHP's place: crystals; the four pools (each `BottleWithRandom` is a `getBottle()` draw); medallions;
`fillPrizes` (`randomCollection(15)` over the 14 prize and event locations, the prize shuffle, and fresh pools with
their bottle draws for every prize tried); fountains; prize packs; the three pool shuffles; the location shuffle;
random picks for maps and compasses; the Ganon's Tower junk count and locations; the item shuffles; `setTexts` (uncle,
blind, tavern man, Ganon's lines, the two Progressive Bow picks or the fake silvers line, the triforce text);
`randomizeCredits` (seven shuffles and the smithy coin flip); `HintService` (tiles, pick list, five pick shuffles, each
hint's own name arrays, the hintable items, a random location per hinted item, the extra hint count and locations,
joke hints); then in the writer the prize music (only with maps on pickup), the digging game, the 1024-byte RNG block
and the drop pool.
`z3_rng_int(n, n)` now draws once, as `mt_rand` does. `z3_rng_init_mt` runs the same calls on PHP 8.1's MT19937 and
`php_mt_rand_range32`, so a C run seeded like `oracle_seed(n)` should match the oracle's draws one for one.

**PHP behaviour kept on purpose.**
- `World::$collected_locations` persists between sweeps (`Z3Collected`, reset where PHP resets it). Link's Uncle's fill
  rule (`Sanctuary canAccess(collectItems())`) therefore sees only what the filler's own sweep left unmarked, as in PHP.
- `checkWinCondition($items)` runs `collectItems($items)`, which adds the pre-collected items a second time.
- Shop inventories are collectable locations (shops' region and requirement), so a reachable shop's Ten Bombs count.
- `removeUnclesSword()` runs when Uncle holds the UncleSword alias (an alias is no `Item\Sword`), and the shield is
  always removed (the `||` in `writeToRom`).
- `InitialSram`'s `'Progressivebow'` case never matches; `heartCount(0) < 1` is true only with no Health item at all.
- The filler stops scanning at the first fillable location except for maps and compasses (which draw among all of
  them): the rest of PHP's filter only touches the collected list, which the next item resets.

**Texts.** Ported (see the table). What the PHP does and the C keeps:
- `setTexts` swaps the first of two random Progressive Bows for `new Item\Bow('ProgressiveBow', [0x65])`: the
  location still holds a Progressive Bow for logic and texts, writes byte 0x65 (`Z3Seed::bow_alt_loc`), and is no
  longer found by `getLocationsWithItem(ProgressiveBow)` (another object, so `==` fails), which the hints see.
- `HintService`'s three location pairs never give a hint: `in_array($location->getName(), $pick)` compares "Name:1"
  with bare names, the collection comes back empty and `getHint()` is null, so the pick is skipped (no draws).
- The hint names keep Laravel's fallback: a missing `hint.item.*` key (ProgressiveBowAlternate, ShopKey, ShopArrow,
  Crystal) is the key itself.
- `LocationCollection::merge` keys by location name, so a hinted location already among the random ones keeps its
  first place.
- With hints off only `sign_north_of_links_house` changes ("Randomizer v31"), and nothing is drawn.
- `setMysteryMasking` (spoilers "mystery") is not in the first release.

## Step 9 (first part): the Enemizer's boss shuffle

alttpr hands a boss-shuffled world to the Enemizer (`Enemizer::randomize`: `EnemizerCLI.Core` with `UseManualBosses`,
the bosses `placeBosses` chose, every enemy, damage, health and pot option off) and writes back its base patch and the
bytes it logged. The binary in alttpr's lock is `z3/enemizer_linux` 6.1.0.180, built from the `alttpr-com` branch of
cassidoxa/Enimizer (`e7b5299`, "Fix SNES to PC conversion"; the 2 MB ROM layout), a fork of Zarby89/Enemizer (MIT,
Copyright (c) 2023 Zarby89). The `linux-build-0.1.0` tag of the same fork is older: its data files differ from the
image's, `alttpr-com`'s match them byte for byte.

| File | What |
|---|---|
| `tools/z3/gen_z3_enemizer.py` -> `core/z3gen/z3_enemizer_gen.{h,c}` | `enemizerBasePatch.json` (59 records, 15527 bytes) and the PC addresses of the five symbols the boss writes use (`exported_symbols.txt`), both taken from the oracle image |
| `core/z3gen/z3_enemizer.{h,c}` | `Randomization::MakeRandomization` for these options: `ExpandRom` (0x7FD7, the version string "6.0.32"), the seed string "EN<seed>", `OptionFlags::ToByteArray`, the base patch, the blind door and sprite flags, `ManualBossRandomizer`/`BossRandomizer::WriteRom` (sprite pointers, room header graphics, Trinexx and Kholdstare shells moved into other rooms' object data, which `DungeonObjectDataPointerCollection` rewrites into the modified room table, Ganon's Tower 1 and 2's new sprite lists, Blind's spawn code, the Thieves' Town maiden), Retro's bush table, `BootlegMagic`'s Moldorm eye count from .NET's `System.Random(seed)`, the Agahnim flag, Trinexx's ice floor, `SetHeartBeepSpeed(Quarter)` |

`z3_generate` runs `z3_enemize` after `isWinnable` and before the tournament flag, as `prepSeed` does, with
`z3_enemizer_seed(seed)` as the Enemizer's seed (alttpr: `random_int(1, 999999999)`; here a stream of its own, like the
hash icons). Everything the Enemizer writes for these options goes through its logged setters, so the C writes straight
onto the ROM in the Enemizer's order. The ROM stays 2 MB: the Enemizer grows its own copy to 4 MB, but nothing it logs
lies past 2 MB, and alttpr's ROM keeps its size.

Kept as the Enemizer does it:
- `ExpandRom` writes 0x0C (4 MB) into the header's ROM size byte, and every boss-shuffled ROM gets heart beep 0x80
  (alttpr sends `HeartBeepSpeed` 2, which is `Quarter`); a cosmetic heart beep set afterwards still wins.
- `DungeonObjectDataTable::Length` counts a door of the first two layers as three bytes and leaves out the closing
  0xFFFF, so the next moved room starts there (gap or overlap) and the last room keeps its extra 0xFFFF.
- Rooms are written in room id order; Turtle Rock's and Ice Palace's rooms count as modified whenever their shell is
  taken out, even when no Trinexx or Kholdstare went elsewhere. Arrghus in Ganon's Tower 1 keeps only two fairies.
- Vitreous's room gets graphics 22 (Kholdstare's; the Enemizer's own "TODO: really?").

Options table: `boss_shuffle` (None, Simple, Full, Random; default none) comes last, after `quickswap`, so every
earlier entry keeps its index. `Z3GenSettings::boss_shuffle` is appended (0, none, by default); `z3_generate` returns
-6 if the Enemizer's writes fail (a boss it has no data for, room data that does not parse; never seen).

## Checks run (2026-11-24)

Scratch readers outside the repo, both sides seeded the same way (`oracle_seed(n)` in the container, `z3_rng_init_mt(n)`
in C). Settings drawn over the whole first-release table (Open/Standard, four goals, crystals 0-7 or random for each,
four dungeon item modes, three accessibilities, Basic/Advanced, four sword modes, Normal/Hard/Expert pool and
functionality; hints off and tournament on in about a quarter of the cases each; heart beep, menu speed and quickswap
in the last 600 ROM cases), with the default preset every fourth case.

| Check | Cases | Result |
|---|---|---|
| `vectors`: ItemCollection helpers and `Boss::canBeat` | 5050 inventories, 257550 values | all equal |
| `worldvectors`: `canEnter`/`canComplete` per region, `canAccess` per location | 5300 cases (2468 Open, 2532 Standard in the 5000 batch), 1526400 values | all equal |
| `placementbatch` vs `z3_fill` (MT) | 4848 seeds, 1144128 locations; `isWinnable`; the last 1800 also pre-collected items and bosses | all identical, none errored, all winnable on both sides |
| `checkplacement` (PCG32 fills read back by the PHP) | 2430 | all winnable; 2429 meet their accessibility, 1 does not (below) |
| `placementrom`/`rombatch` vs `z3_generate_rng` (MT), hash icons and seed string pinned | 904 ROMs | all byte-identical, texts, credits and hints included |
| Dialog encoder vs `convertDialogCompressed` | 831 strings (every pool, every location text, samples with arrows and ellipses) | all equal |

Accepted as alttpr's own behaviour:
- With 100% Inventory an Advanced, Vanilla-swords, Fast Ganon fill can leave half the world unreachable while the seed
  stays winnable (one PCG case of 2430). It is not the port: the same settings on MT seed 7000138 make the identical
  placement in the PHP (`placementbatch` equal) and the PHP's `checkplacement` reports the same 83 unreached
  locations; 1 seed in 2000 does it. The check therefore counts as violations only what 100% Inventory leaves out

## What remains

- The rest of the Enemizer: enemy shuffle, enemy damage and health, pot shuffle (`enemizer.*` other than boss
  shuffle). `z3_enemize` covers only the writes alttpr's options make with all of them off; the oracle can already
  run the real Enemizer with them through a case's `extra` settings.
- Hosts: `boss_shuffle` is a new last row of `Z3_OPTIONS` and a new last field of `Z3GenSettings`; the ROM is still
  2 MB, and `z3_generate` can now return -6. Hosts that copy `core/z3gen/z3_*.[ch]` get `z3_enemizer.c` and
  `z3_enemizer_gen.c` with it.
- The customizer (plando JSON) and `setMysteryMasking`.
- Hosts: Inverted fails its fill about one seed in twelve on both sides (`z3_generate` returns -3), so a host retries
  with the next seed number, as SMZ3's does.
- `z3_generate` keeps a static `Z3Seed` and `z3_fill` static lists (not reentrant). `Z3Seed` holds a pointer to its own
  `col`: copy it only with `w.col` re-pointed.

## Open problems

- Fixed here: `World::collectItems()`'s persistent collected list (now `Z3Collected`); shop inventories in the sweep.
- `ItemCollection::has($x, null)` is false in PHP but `z3_has(x, 0)` is true: only `item.Goal.Required`, which
  `z3_cfg_derive` sets for the hunt goals, can be missing.
- The Blacksmith's address depends on `region.swordsInPool`; the tables keep the default (true) one.
- `z3_sram_starting_equipment` applies items in item-id order, PHP in insertion order. Only bottle slots or a sword
  and shield both pre-collected could differ; the release's pre-collected items (three heart containers, capacity
  upgrades, Uncle's sword when assured, Rescue Zelda) do not.
- `setupCustomShops` assumes `Z3_SHOPS` order is PHP's `ShopCollection` order (regions, then constructor order), which
  is how the transpiler builds it.
- Without a database the PHP writes the five hash icons and the seed string only when saving a seed record, so the
  oracle pins both (icons from the C run, "VT <seed>"); every other byte comes from the same draws.
- A chosen "0" crystals for the tower does not pre-open it (only a random 0 does): `prepSeed` passes the request's
  string to `crystals.tower === 0`. Kept, `z3_rom_write` reads `Z3GenSettings::crystals_tower < 0`.
