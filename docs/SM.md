# Super Metroid generator (`core/smgen/`): progress

C port of tewtal's standalone Super Metroid randomizer (`Randomizer.SuperMetroid`, "Super Metroid Item Randomizer"
v3.1, MIT), step 2 of `STANDALONE.md` (Generators > Super Metroid). Same method as `PORT.md`: the C# stays the oracle,
logic and tables are generated by script, the filler and patcher are ported by hand on `core/gen/smz3_rng.c`.

Every `.c` in `core/smgen/` (and the generated `build/smgen/sm_ips_data.c`) compiles with `gcc -std=c99 -Wall -Wextra -c`
without warnings, and they link together with `core/gen/smz3_rng.c`. None of it has been run.

### 1. Oracle: `tools/gen-cli-sm`

The project compiles the vendored `Randomizer.SuperMetroid/**/*.cs` and `Randomizer.Shared/Contracts/IRandomizer.cs`
into itself, so the internal `World`, `Item`, `Filler` and `Patch` classes are reachable without touching the vendored
code and without the EF Core/Npgsql dependencies of `Randomizer.Shared`. Targets net10.0 (the only SDK here); .NET's
seeded `Random` is still the legacy algorithm there.

- `vectors <count> <rngseed> <out>`: random inventories and every `ItemListExtensions` helper (`CanIbj` ...
  `CanDefeatDraygon/<logic>`, `HasEnergyReserves/0..8`).
- `worldvectors <count> <rngseed> <out>`: random logic and inventory, every region's `CanEnter` (World.Regions order)
  and the ids of the locations `Available`.
- `placementbatch <cases.jsonl> <out>`: one `{"seed":"123","logic":"tournament","placement":"split","race":false}`
  per line, through the real `Randomizer.GenerateSeed`; writes `locs id:itemtype ...` and every seed patch
  (`patch ADDR HEX`) sorted by address, without the two GUID fields.
- `rom <sm.sfc> <sm_randomizer.ips> <seed> <logic> <placement> <race> <out.sfc>`: the whole 4 MB ROM as
  `Randomizer.CLI` builds it (SM ROM padded to 4 MB, base IPS, seed patches), GUID fields zeroed.
- `schema <out.json>`: `RandomizerOptions.List`.

### 2. Logic and world

`tools/port_world_sm.py` reads `Item.cs` (ItemType values and the `ItemListExtensions` helpers), `World.cs` (region
order) and the 16 region files, and writes `sm_world_gen.{h,c}`: `SM_ITEM_*`, `SMREG_*`, the helpers as `sm_Can*`,
`sm_can_enter_<Region>(logic, p)`, the one private helper (`CrateriaWest_CanEnterAndLeaveGauntlet`),
`sm_loc_access(id, logic, p)` and the 100-location table in `World.Locations` order (id, name, type, class, region,
PLM address). `Logic switch { Casual => a, _ => b }` becomes a conditional on the `logic` argument, so one table serves
both logics; && chains under || get brackets for `-Wparentheses` (same meaning). The inventory is `SmProg`, a count
per ItemType: the C# logic only asks `Has(type)`, `Has(type, n)` and tank counts. `sm_HasEnergyReserves` is
hand-written in `sm_world.h`; `sm_world.c` holds `sm_loc_available` and `sm_loc_index`.

`cs_regions.py` is reused for its C# bracket and argument splitting; `port_world.py` is not touched (it is bound to the
Cas' tracker world). The SM regions have no rewards, bosses, keys or `Allow` rules, so `CanFill` equals `Available`.

### 3. Pools and filler

`sm_fill.c` follows `Randomizer.GenerateSeed` up to the patch seed: `Random(seed)` (re-seeded from `Next()` for Race),
the three pools (`CreateJunkPool` draws 62 `Next(7)`), then `Filler.Fill`: InitialFill (Morph, Missile or Super,
a bomb-wall breaker from `Next(8)` or a Power Bomb for Split+Casual, then Super/Power Bomb for Split), PriorityFill of
Varia and Gravity (without `CanPlaceAtLocation`, as in the C#), AssumedFill, then FastFill of the nice and junk pools,
and `patch_seed = Next()`. Lists keep the C# order (stable `Remove`, `Add` appends) and every `Shuffle` draws the same
`Next(n + 1)` sequence, so the RNG stream should match. Kept as upstream on purpose: the Varia rule tests the area
"LowerNorfair", which no region has ("Norfair Lower"), so it never fires. Where the C# would loop forever (an item with
no location), the C gives up after 4096 passes (-2). `sm_playthrough_ok` is `Playthrough.Generate`'s check.

### 4. ROM

`tools/build_sm_ips.sh` copies the submodule to a temp folder and runs its own `build.sh` with asar 1.81 (00/FF dummy
ROMs of 4 MB, `create_ips.py`, then the six `randopatches/ips/*.ips` merged in). Result: `patches/sm_randomizer.ips`,
548412 bytes, MD5 `eae33d903692245d443ef62c9f538916`, highest write 0x3FFF60, so the output ROM is 4 MB (0x400000),
as both the web client (`rom.js`) and `Randomizer.CLI` build it. `tools/gen_sm_ips_c.py` turns it into
`SM_BASE_IPS[]`; like `ips_data.c`, it is generated at build time (`build/smgen/sm_ips_data.c`), not kept in the tree.

`sm_patch.c` ports `Patch.Create` in its order: item PLM per location (type offset +0x54 Chozo, +0xA8 hidden), player
name "PLAYER" at 0x1C5000, seed data at 0x1C4F00 (world id, config word, seed, GUIDs), seed hash at 0x2FFF00
(`NextBytes(4)` from `Random(patchSeed)`), the credits list of major items at 0x2F5240, one "Save the animals" IPS
(`Next(Count - 1)`, so the tenth, "sets the timer low", is never picked; data copied by `tools/gen_sm_patchdata.py`),
and the title `SM3.1T0000007B` at 0x7FC0. The item table at 0x1C6000 and the flag at 0x277F00 are written only for
multiworld upstream, so not here. No checksum is written, as upstream.

The credits walk the locations `OrderBy(Region.Name).ThenBy(Name)` with .NET's culture comparer. The order is fixed, so
`port_world_sm.py` sorts it once with an emulation of ICU root collation (case after letters, space and punctuation
below digits and letters) into `SM_CREDITS_ORDER`. If the oracle machine runs .NET with invariant globalization
(ordinal sort), this order differs ("Missile (Crateria" before "Missile (blue"); `placementbatch` shows it.

### 5. Options and entry point

`tools/gen_sm_options.py` reads `RandomizerOptions.List` and the `[Description]`/`[DefaultValue]` attributes of
`Config.cs` into `SM_OPTIONS` (logic, goal, placement, race; game mode and players are multiworld only, the seed is
taken apart). `sm_option_set(s, key, value)` takes the C# keys and values. `sm_generate(s, sm_rom, out_rom, out_cap,
ids, seed_out, hash_out)` pads the JU ROM to 4 MB, applies the base patch, fills, checks the playthrough and patches.
Defaults (`sm_settings_defaults`): Tournament, Split, not Race.

## Checks ready to run (none run, waiting for the owner)

1. Logic: `gen-cli-sm vectors` against the C helpers, and `gen-cli-sm worldvectors` against `sm_region_can_enter` /
   `sm_loc_available`. Needs a small C reader for the vector files (not written: no test files without a yes).
2. Filler: `gen-cli-sm placementbatch` on random seeds for Casual/Tournament x Full/Split x Race, compared with
   `sm_fill`'s `item_at` (by location id).
3. Patches: the same batch's `patch` lines against the bytes `sm_patch` writes (credits order included).
4. ROM: `gen-cli-sm rom` against `sm_generate` with `ids = NULL`: byte-identical 4 MB ROMs expected.

## Open problems

- GUIDs. The C# writes two `Guid.NewGuid()` strings at 0x1C4F10 and 0x1C4F30, so no two C# ROMs are equal there.
  The C writes zeros or the caller's strings; the oracle leaves them out. What reads them in the ROM (seed display,
  multiworld) is not checked yet.
- Playthrough on Race. The C# runs the playthrough check only when it makes a spoiler (not Race); the C checks
  every seed. A Race seed that fails would be an error in C and a ROM in C#; the filler should make that impossible.
- Seed hash on screen. The base patch has `randopatches/seed_display.asm`; how it draws the four bytes at 0x2FFF00
  (and whether the tracker can show the same) is still to read.
- End of run. Not looked at yet (`STANDALONE.md` asks for the ship signal from the base ASM).
- Host wiring. No frontend builds `core/smgen/` yet; the Makefiles need `core/smgen/*.c`, `core/gen/smz3_rng.c` and
  the generated `sm_ips_data.c`.
